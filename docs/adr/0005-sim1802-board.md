# 0005 — The sim1802 virtual board: ROM boot, memory profiles, devices

Status: **Proposed — needs Alan's acceptance (Step 03 exit criterion)**
Date: 2026-09-29 (revised the same day after Alan's review, see below)
Step: step-03

## Context

NuttX needs a board: memory map, reset path, console, tick and a way to end
automated tests. The simulator (ADR 0003 fork) has 64 KiB of memory, an I/O
controller on ports 6/7, and — upstream — an ELF *program loader* that
places segments, writes boot arguments to the top of RAM, starts with zeroed
RAM and registers, and jumps to any entry point through a small bootstrap.
The contract asks for two memory profiles (SIM64 and HW32/32) and a board
layer that stays clean for real hardware.

**Alan's requirement (review of the first version):** "you need to use a ROM
option to sim1802 that be exactly like the real machine. This way we could
write the binary on the ROM and get it booting correctly on real machine."

## Options considered

1. **RAM-only image, loaded by the simulator's ELF loader.** Simplest, but no
   reset code, no `.data` copy, no ROM: models no real board.
2. **ROM-at-0 layout, still started through the ELF loader** (the first
   version of this ADR). Right layout, but the simulated machine still starts
   with zeroed RAM/registers and loader-written memory, so code that only
   works because of that would pass in the simulator and fail on hardware;
   and the tested artefact is the ELF, not the bytes in the EPROM.
3. **ROM-at-0 layout, booted from the raw ROM binary** with the simulator
   modelling power-on like the hardware (fork `--rom` mode).

## Decision

Option 3, as documented in [`docs/cdp1802/board-sim1802.md`](../cdp1802/board-sim1802.md):

- **The build artefact is the ROM binary** `nuttx.bin` (`objcopy -O binary`),
  the exact EPROM contents, and **that file is what the simulator boots**
  (`sim1802 --rom`, via `scripts/run.sh`). Power-on state as on hardware:
  unprogrammed ROM = 0xFF, RAM and the registers reset leaves undefined are
  pseudo-random (seeded, reproducible), nothing is written before the first
  instruction, ROM writes are ignored, the console is 8-bit clean.
- reset at 0x0000 from the documented reset state [MPM p. 72]: `DIS` with
  inline byte 0x00, then PC := R3 (R0 is then free: the board has no DMA);
- **HW32/32**: ROM 0x0000–0x7FFF, RAM 0x8000–0xFFFF. This is the profile used
  for feasibility judgements;
- **SIM64**: ROM exactly as large as the image, RAM from there to 0xFFFF;
- in both, `.data`'s initial values are in ROM and copied to RAM at start-up,
  and `.bss` is cleared — nothing may rely on RAM contents at power-on;
- devices: the fork's console (IRQ 6), cycle-driven timer (IRQ 0), cycle
  counter and HALT, all through ports 6/7, known only to the board layer;
- a nominal CPU clock `CONFIG_BOARD_SIM1802_CLOCK_HZ`, default 4 MHz (MPM's
  example clock), used to turn `CONFIG_USEC_PER_TICK` into a timer period;
  the default tick is chosen in Step 07 from measured interrupt cost.

Simulator changes this needed (fork, `cdp1802-nuttx`): `--rom` mode
(`f41d9eb`), 8-bit clean console (`a3d1933`, bytes ≥ 0x80 were UTF-8
encoded), `__sim1802_rom_end` (`bef5700`) and loading ELF segments at
`p_paddr` (`1be386b`) so that the ELF path used by validation programs agrees
with the ROM path.

## Consequences

- The same `nuttx.bin` that passes the simulator tests is the file to program
  into a 32 KiB EPROM for a real board with this memory map; only the
  board-specific drivers (console, timer, halt) would differ on hardware.
- Start-up code (Step 06) must initialise everything itself: copy `.data`,
  clear `.bss`, set every register it uses. Mistakes show up in the simulator
  (verified with a smoke build that omits the `.data` copy).
- HW32/32 is executable, not just a size estimate: an image that does not
  fit fails to link.
- `smoke.S` + `sim64.ld`/`hw32.ld` are the prototypes for the NuttX linker
  scripts in `boards/cosmac/cdp1802/sim1802/scripts/` (Step 05).
- Program arguments (argv) do not exist in ROM mode, as on hardware.

## How to revisit

A different RAM/ROM split (e.g. 16/48) is a new linker script and a new
profile row in the size budget. If NSH does not fit in HW32/32 (Step 10), a
banked profile would need a new ADR. Real hardware bring-up (out of scope)
would add a board directory with real drivers and reuse the arch/chip layers
and the same ROM layout.
